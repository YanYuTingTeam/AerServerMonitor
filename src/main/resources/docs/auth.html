鉴权

系统采用 纵深防御 (defense in depth) 设计, 三条入口分别独立鉴权, 但共用相同的 HMAC 时间戳防重放思路.

三个入口

1. 外部 API — 仅 HMAC-MD5 (salt + body/origin)

2. Dashboard — JWT + HMAC-SHA256 (jwt + body) 双重校验 + CSRF Origin 防护

3. WebSocket — 握手时 JWT + HMAC-SHA256 (jwt + "ws-handshake:" + a) 校验

一. 外部 API — HMAC-MD5 鉴权 第三方调用

第三方程序调用 /player/* / /server/* / /chat/* / /system/* / /log/* 接口时, 必须携带以下两个请求头. 不要同时携带 Authorization 头 — 否则服务端会按 Dashboard 路径处理, 要求 SHA-256 双重校验, 校验失败.

Header说明
a当前毫秒级时间戳. 仅容许 header-a-timeoffset 误差 (默认 15000ms)
bHMAC-MD5 加密后的值 (16 进制). 算法和 salt 可在 config 修改

加密规则

// 伪代码
String data;
if (method == GET || method == HEAD) {
    data = config.get("hmac-origin");  // 默认 "AerServerMonitor"
} else {
    data = requestBody;                // 整个 POST body
}
String header_b = HmacMD5(config.get("hmac-salt"), data);

curl 示例

# GET /player/info?uuid=xxx
A=$(date +%s%3N)
B=$(echo -n "AerServerMonitor" | openssl dgst -md5 -hmac "AerServerMonitor" | awk '{print $NF}')
curl -H "a: $A" -H "b: $B" "http://localhost:8009/player/info?uuid=xxx"

# POST /player/kick?uuid=xxx
A=$(date +%s%3N)
BODY='You are kicked'
B=$(echo -n "$BODY" | openssl dgst -md5 -hmac "AerServerMonitor" | awk '{print $NF}')
curl -X POST -H "Content-Type: application/json" -H "a: $A" -H "b: $B" \
     -d "$BODY" "http://localhost:8009/player/kick?uuid=xxx"

算法说明

外部 API 默认使用 HmacMD5 (在 config.yml > options.hmac-algorithm 中可改为 HmacSHA256). 选择 MD5 是为了与原始开发规范保持一致.

外部 API 路径不做 CSRF Origin 校验 — 这是设计上允许第三方程序跨域调用.

二. Dashboard — JWT + HMAC-SHA256 双重校验 + CSRF 防护 内置前端

内置 Dashboard (路径 /dashboard) 使用 JWT + HMAC-SHA256 双重校验. 即便 JWT 从日志或 Referer 泄露, 攻击者仍需正确计算 HMAC 才能伪造请求. 同时通过 Origin 校验防御 CSRF.

2.1 登录流程

  1. 调用 POST /api/auth/login 用账号密码换取 JWT token (无需 a/b 头, 但需通过 Origin 校验).
  2. JWT 包含 admin_id / username / role / token_version / exp.
  3. 改密后 token_version 自增, 所有旧 token 立即失效.

2.2 后续请求 — 每个请求都需同时携带

Header说明
AuthorizationBearer <jwt> — 服务端校验签名 (HMAC-SHA256 + dashboard.secret) / 过期 / token_version
a当前毫秒级时间戳. 与外部 API 共用同一容差配置
bHmacSHA256(jwt, body || "") — 用 JWT 本身做 key, 无需暴露全局 salt 给浏览器

2.3 b 头加密规则

// 前端 (dashboard/js/api.js + dashboard/js/hmac.js)
const token = localStorage.getItem('token');
const a = Date.now().toString();
let data;
if (method === 'GET' || method === 'HEAD') {
    data = '';                  // GET: 空字符串
} else {
    data = JSON.stringify(body); // POST: 整个 body
}
const b = HmacSha256(token, data);  // 纯 JS SHA-256 实现, 兼容 HTTP 非 secure context

// headers
headers['Authorization'] = 'Bearer ' + token;
headers['a'] = a;
headers['b'] = b;

为什么用 JWT 做 HMAC key, 而不是全局 salt?

浏览器是公开客户端, 任何写在 JS 里的密钥都能被攻击者读取. 用 JWT 本身做 key 实现"请求级密钥", 即便全局 salt 泄露也无法伪造请求, 因为攻击者拿不到当前会话的 JWT.

为什么用纯 JS SHA-256 而不是 Web Crypto API?

crypto.subtle 仅在 secure context (HTTPS / localhost / file://) 下可用. BungeeCord Dashboard 通常通过 http://vps-ip:8009/dashboard/ 访问, 是非 secure context, crypto.subtle 会是 undefined. 纯 JS 实现任意上下文都能工作.

2.4 CSRF 防护 — Origin / Referer 校验

所有 POST / DELETE / PUT 请求强制校验 Origin (或 Referer) 头:

  • 同源: Origin 的 host == Host 头 → 放行
  • 白名单: Origin 在 options.dashboard.allowed-origins 中 → 放行
  • 其他 → 403 拒绝
  • GET / HEAD / OPTIONS 不校验 (安全方法不改变状态)
# config.yml
options:
  dashboard:
    allowed-origins: []   # 空 = 仅同源; 跨域访问填如 ["https://monitor.example.com"]
    csrf-protection: true # 关闭后 POST 不校验 Origin (不建议)

/api/auth/login 是无鉴权 POST, 同样走 Origin 校验, 防止 login CSRF (攻击者诱导用户在恶意页面提交登录表单到本服务).

2.5 CORS 收紧

响应头 Access-Control-Allow-Origin 不再写死 *, 改为按 Origin 动态回显:

  • 同源或白名单 Origin → 回显该 Origin + Vary: Origin
  • 其他 → 不设 ACAO, 浏览器自动拒绝跨源响应
  • 不设 Access-Control-Allow-Credentials: true — 因为我们用 Authorization 头 (非 cookie) 鉴权, 浏览器不会自动带凭据

三. WebSocket — 握手时 JWT + HMAC-SHA256 校验 实时推送

WebSocket 端口 = HTTP 端口 + 1 (默认 8010). 浏览器 WebSocket API 不允许自定义请求头, 因此鉴权信息通过 查询参数 在握手阶段传递:

3.1 连接 URL

ws://<host>:<ws-port>/?token=<jwt>&a=<毫秒时间戳>&b=<HMAC>

3.2 b 头加密规则

// 前端 (dashboard/js/ws.js)
const token = localStorage.getItem('token');
const a = Date.now().toString();
// 关键: "ws-handshake:" 前缀做上下文绑定, 防止 HTTP API 的 a/b 头日志被拿到 WS 重放
// a 也绑入 b, 防止在 15s 窗口内单独重放 a
const b = HmacSha256(token, 'ws-handshake:' + a);

const url = `ws://${host}:${wsPort}/?token=${encodeURIComponent(token)}&a=${a}&b=${b}`;

3.3 服务端校验 (在 HTTP 升级握手阶段)

  1. JWT 校验: 签名 + 过期 + token_version (与 Dashboard 同源)
  2. a 时间戳容差: |now - a| <= header-a-timeoffset (默认 15s)
  3. b HMAC 校验: b == HmacSHA256(token, "ws-handshake:" + a)
  4. 连接数限制: sessions.size < ws.max-connections (默认 500)

任何一项失败: 返回 HTTP 401, 不进行 WebSocket 升级. 浏览器收到非 101 响应后会触发 onerror + onclose.

WS 鉴权失败不会跳登录

握手阶段的 401 是 HTTP 响应, 不会升级到 WebSocket, 浏览器无法区分"鉴权失败"和"服务不可达". 前端 ws.js 在 onclose 时统一走指数退避重连; 如果 JWT 过期, 重连会持续失败. 用户需手动刷新页面 (触发 /api/auth/verify 跳登录).

3.4 鉴权通过后

channel attr 记录 admin_id / admin_name 便于审计. 客户端发送 {"action":"subscribe","events":["all"]} 后开始接收事件. 服务端会自动推送 __batch 批量消息 (100ms 窗口聚合, 队列上限 50k), 前端展开后逐条派发.

四. IP 白名单

服主可在 config 中开启 IP 白名单鉴权 (在 HMAC/JWT 校验之前). 支持精确 IP 和 CIDR 网段 (如 192.168.0.0/16).

options:
  ssrf-protection:
    enabled: true
    mode: "whitelist"   # 或 "blacklist"
    whitelist:
      - "127.0.0.1"
      - "192.168.0.0/16"
      - "10.0.0.0/8"

五. 速率限制

每个 IP 在 per-time (默认 2000ms) 窗口内最多 max-request-per-time (默认 3) 次请求. 超限返回 429 + errcode 50003. 持续超限可能触发临时封禁.
